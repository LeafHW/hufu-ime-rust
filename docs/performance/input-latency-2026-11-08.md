# 输入延迟修复（2026-11-08）

基准提交：`8fc1d213c8dc9204836ef80acbe49c0394867d4a`。

此前把 server 从 BelowNormal 提至 AboveNormal，已改善 CPU 争用下的输入线程调度饥饿；它没有消除管道轮询等待、Host 争锁和大皮肤快照复制。本次针对这些独立原因修复，开发与构建均使用独立工作树、分支及 target，未改跟打器源码、原工作区、安装文件或发行版本。

## 变更

- Windows 管道改为 OVERLAPPED I/O 与内核事件唤醒，移除 `PeekNamedPipe` 后的 10ms 轮询睡眠。首帧 10s、未完成帧头/正文 2s 的防护保留，写响应也有截止时间。取消后先收割完成，再释放 OVERLAPPED、event 与缓冲。
- server 进程使用 Normal；专用管道线程设为 Highest（相对 +2），保持输入基础优先级 10。后台普通线程恢复基础 8，Rust 重排池相对 -1 为基础 7，重排 owner 线程同时降低优先级并请求 EcoQoS。保留半核亲和；没有假定 native DLL 内部线程继承 owner 的线程策略。
- 完整方案、全局注释/拆分与启用的转换字典，在 Host 锁外准备后应用。Ctrl+M 的旧大码表复用原预载 worker 析构。目录监控、托盘、HTTP 与 pipe 共用预载校验，防止旧配置、同名重载或 A→B→A 结果覆盖新状态。
- 启动反查预热、设置页整句预览、皮肤/图片/声音/方案文件读取、滚轮字号保存、剪贴板与控制台光标查询移出输入 Host 锁。皮肤跨文件清扫与滚轮保存使用独立编辑锁并按同目录临时文件替换；编辑锁先于 Host，普通按键不获取编辑锁。
- `Shared.skin` 使用 `Arc<Value>`；SSF 每帧只复制所需绘制配置，完整挂件仍从原快照同步。首显单位宽度改为瞬时参数，避免小字段触发大图片深拷贝。
- 每键附带皮肤版本与方案，已载快照匹配时免首显额外查询。旧 server 保留原兼容逻辑；失败保留有效快照，400ms 内不反复同步重试，新版本/方案解除旧失败冷却。
- posted 动画消息发现待处理输入时跳过当前拍，后续按实际时间推进。没有改变动画时长、曲线或帧网格，也不能中断已开始的 Present。
- 补充语料使用显式失效的不可变缓存；整句注入词按编码索引，保留原词序、Unicode 边界及同码去重语义。解码与词图更新统一锁顺序，避免一次解码混用两代词图。

## 本机测量结果

管道直接引用实际实现，两轮各 120 个样本，交换新旧顺序。未加专门竞争负载的组仍可能有系统后台活动和本轮独立 TSF 测试诊断，不代表严格控制的整机空闲环境。

| 管道场景 | 原实现 p95 | 新实现 p95 |
| --- | ---: | ---: |
| 连续无间隔请求 | 0.0308ms | 0.0909ms |
| 固定 83ms 间隔 | 9.9121ms | 0.0755ms |
| 随机 25–110ms 间隔 | 9.5405ms | 0.1051ms |
| 单核与一条 Normal 负载竞争，随机间隔 | 10.8191ms | 0.0770ms |

新实现的事件创建/释放使连续吞吐多出几十微秒开销；正常键间隔不再白等轮询周期。单核竞争下新实现最大值仍为 3.8813ms，不提供严格实时上界。以后若连续吞吐成为瓶颈，可研究安全地复用每连接 event。

实际皮肤投影 helper 微基准，13,981,016 字节挂件：原深拷 p95 4.3043ms，Arc 快照与新投影 p95 0.0010ms；该测试投影只有160字节，不含完整绘制。

400条补充语料、空 mock decoder 隔离测试：分配从1854次/键降至31次/键，原两轮130–158µs/键，新两轮约2.44µs/键。真实六句普通整句逐键 p95 前后仍约19–22ms，与轮间波动重叠；本批没有证明普通整句计算显著提速。

## 保留的优化方向

1. TSF 的同步 IPC 仍有分段超时与 BG 连接锁。后续应统一一次操作总预算，并覆盖超时后组字恢复、重复提交和断连重试语义。
2. SSF 冷读图/解码、Present 与窗口操作仍可能占宿主 UI 线程。异步首帧及独立绘制线程需要额外验证资源归属、换皮失效和候选可见时序。
3. 整句主解码仍同步；新索引主要改善大量注入词场景，不应宣称普通整句计算已消失。应继续测长组字、用户词规模与实际模型的 p95/p99。
4. 反查首次使用及按键直接切繁简的懒加载、补充语料重读、配置/调整文件持久化、部分通用资源替换的析构仍有同步路径。磁盘/分页压力下需单独测量，再将最慢路径分批移出输入锁。
5. native 重排 DLL 的内部线程策略没有接口保证。现有半核亲和只能约束其 CPU 范围，不能代替 DLL 内部线程数/优先级控制或进程隔离。

本次分支不直接部署基于旧跟打器快照构建的 server。与并行开发成果合并后，应在独立测试环境检查实际宿主、两种位数、JSON/SSF 动效与高负载输入，再进入部署或发行流程。
