# 整句概率查询复用验证（2026-11-09）

基准为第一批延迟修复提交 `ac68a416cf07467ea337c114f925f2c1cd767f8f`。本轮只优化整句解码中重复的五阶模型查询，保持原模型、概率计算、浮点操作顺序、候选排序、束宽、剪枝和提前上屏规则。开发与探针在独立 C: 工作树进行，未修改 DSH 跟打器、原工作区或安装文件。

测量先于实现。对现有逐键探针插桩后，30 个有效码位的一组解码累计 474,871 次模型查询，只有 88,882 组不同的完整历史与目标；两次长输入增量解码累计 5,800 次查询，只有 526 组不同参数。计数混合了逐键与完整解码，仅用于确认重复计算，插桩耗时不作为最终提速数据。

实现将 `([prev4, prev3, prev2, prev1], target_cp)` 映射到原 `Lm::step_prob` 返回的 `f32`。字符展开及三个 EOS 调用点共用该表，后续 `max(1e-12)`、`ln()`、转 `f64`、score/mass 累加仍在原位置执行。表不参与路径遍历或排序。它仅存活一次解码，最多保存 4,096 项，满后清空并复用容量；满表底层预留约 0.2 MiB，扩容峰值和分配器开销另计。

实测排除了两种有回退的启用范围：

- 中短输入查表收益不足，空表创建也有成本。有效编码长度不超过 16 时，进入单独编译的不缓存实现，连 `RandomState` 都不创建。
- 束宽 1～2 时重复查询太少。有效束宽小于 4（包括 quick/inc 上限）时走同一不缓存实现。
- NM02/NM04 三阶模型也走不缓存实现。

`decode_internal::<false>` 保留不缓存对照，供差分测试。解析后的编码、锁和增量桶直接移入专门实现，没有改变搜索过程。

本轮相关测试共 163 项通过：hufu-engine 111 个单元测试、23 个集成测试，hufu-sentence 29 个测试。其中新增 10 项，使用匿名 mmap 合成模型，无需安装版模型或输入法。它们比较全部 `SentenceDecode` 字段、score/confidence 的 `to_bits()`、各桶 best/mass/order/truncated 和所有状态字段；覆盖四字历史的最早一字不同、BOS/EOS、未知字回退、非 BMP 字符、同文多路径质量聚合、quick 剪枝、逐键增量、选重、数字码、用户词更新、超过 4,096 种事件后的容量轮换及 NM02/NM04。

最终 hufu-server release 构建通过（fat LTO、codegen-units=1），没有运行或安装产物。构建检查曾触发 `dlltool.exe` 的 `0xc0000142` 弹窗：受限进程中可复现启动失败；普通进程可启动工具，但向 C: 用户目录生成导入库返回 Permission denied；独立 E: 临时目录的导入库自检成功。完整构建因此使用 `E:\DSH-KF\.testtmp\sentence-1109-toolcheck\target` 与其独立 tmp，LLVM dlltool 和明确的 rust-lld/self-contained 链接器。仅在子进程中设置 PATH/TMP/TEMP/链接器及错误提示模式，未改全局环境、仓库构建配置或 DSH 的 target。保留了初次工具错误及误选 LLVM gcc 链接器的失败日志。可复现命令封装在本机 `.review/sentence/build-server.ps1`，脚本退出时恢复进程设置。

真实模型对照使用 112,622 条的 `D:\HuFu\码表\虎整句`，以及 `D:\HuFu\模型\sentence-fivegram-mobile.bin`（NM03 Q8/version 2，405,663,171 字节）。六句输入为：这是一个关于输入延迟的测试；电脑高负载的时候也应该流畅；今天天气很好我们一起出去走走；这就是所谓的京东自营新鲜水果吗；上网本归类也许真的模糊不过有市场就是硬道理；没有收到货。输入按 `best_code_and_rank(min_len=2)` 冻结生成，缺字立即失败，不把该规则称作所有用户的规范打法。

原版、优化版分别编译为独立 EXE。探针隔离 rich/full/Engine 的缓存，捕获 Engine 自动注入的用户词和补充词后再追加测试词。学习、调频日志、神经重排和 OpenCC 关闭，使用专门数据目录。轨迹包含普通输入、选重、退格重打、翻页选字、提前上屏开关、数字码、用户词和 128 键长组字，比较全部候选字段、浮点位、按键消费、上屏/回删、剩余编码及公开 Session 状态。

2,186 条轨迹、38,522,857 字节的输出完全相同。普通 opt3 和最终发行参数（fat LTO、codegen-units=1）均一致；最终输出 SHA256：

`a2b3745e7d1dd04962c6d15a6853095f0274e3b826763400c89f6fa6bff7e6ad`

最终性能对照使用 Rust 1.98.1、opt3、fat LTO、单代码生成单元。每组先预热，随后测 3 轮；执行顺序为原版 A、优化版 A、优化版 B、原版 B。每个普通输入指标每组 558 键，长组字 384 键。压力组另启动 12 个持续计算线程，机器有 16 个逻辑处理器。每组结束即停止这些独立负载进程。未同时运行编译或其他子任务的性能测试。

没有丢弃异常数据：早期压力试验一次提前上屏普通输入出现 p95=117.79、p99=375.37 ms；后来的固定 CPU 微基准中，原版与优化版都曾出现百毫秒尖峰。没有捕获这些尖峰的系统调度/缺页栈，原因未定。最终版本的两次压力对照没有复现该异常，因此不能断言所有系统长尾已消失，也不能仅凭这些异常给缓存定因。正常组 p50、部分 p99 和少样本的退格/缓存命中指标仍有波动；本报告只宣称上述已重复观察到的改善。
