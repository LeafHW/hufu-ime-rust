# 1.9.9.11：修复 ARM64 安装暂存目录拒绝访问

用户在Windows ARM64安装1.9.9.10，文件解压及载荷预检通过，机器阶段返回
`ERROR: 拒绝访问。 (os error 5)`。现场的HKLM/HKCU、32/64位HuFu COM/TIP均不存在，
失败发生在注册之前。用户关闭旧安装器后，程序和卸载器已回退，码表、数据、备份及日志保留。
本轮没有代用户运行正式安装、注册或清理系统目录。

## 复现和原因

将生产`stage`逻辑抽出可传入私有测试根的`stage_at`，使用已构建的真实载荷，
在用户临时目录中完整执行复制、ACL、清单、三架构加载和目录发布。
修复前稳定失败在 `publish generation <.stage> -> <version-hash>: os error 5`，
并非缺少UAC提权或DLL不能加载。日志见 `stage-before-fix.log`。

独立对照在四个全新目录中复制相同文件：

| 条件 | 立即重命名 | 失败后等待2秒 |
| --- | --- | --- |
| 不启动探针 | 成功 | 不需要 |
| ARM64原生探针，退出0 | 成功 | 不需要 |
| x86仿真探针，退出0 | 拒绝访问5 | 成功 |
| x64仿真探针，退出0 | 拒绝访问5 | 成功 |

见 `move-diagnosis.json` / `diagnose-move.py`。该对照确认仿真程序退出后目录仍会短暂被占用，
没有进一步声称已确定持有句柄的系统进程。Windows的目录移动和删除受句柄/共享权限影响，
参见 [MoveFileEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexa)。

## 修复

暂存目录只执行完整文件/架构/SHA校验，然后先重命名为最终不可变代次；
原生、x86、x64加载探针统一在最终目录执行。所有加载检查通过之后才备份并切换COM/TIP注册。
复用旧代次仍进行完整校验和加载检查；失败不切换注册，不覆盖既有代次。
复制、清单、发布及最终加载错误增加具体操作和路径，清理失败也保留在错误日志中。
生产安装流程没有增加固定睡眠或降低检查标准。

## 本轮验证

- ARM64维护引擎16项回归通过；新生产暂存集成测试单独运行通过。
- 最终1.9.9.11载荷再次执行新暂存集成测试通过；同代次复用和源文件保持通过。
- x64 GNU维护引擎在ARM64仿真下16项回归通过。
- 默认测试列表中的两项ignored分别为超时子进程夹具和需显式载荷的集成入口；
  前者由超时测试实际启动，后者已通过 `--ignored` 单独执行。
- 完整通用构建、最终ARM64三个进程加载预检、独立解包通过：x64 25文件、ARM64 28文件、
  102项发行资源哈希保持。见 `extraction.json`。
- 相对1.9.9.10，两架构仅维护引擎、version.txt及派生清单改变；TSF/桥/后台/评分库/共用GUI
  字节保持，既有对应DLL和渲染证据不因版本号变更而重做。

上述是隔离的文件部署和加载验证，尚未代替用户完成新版真实安装/UAC/输入验收。
原ARM64评分差异仍见 [待办](../../open-items.md)。
