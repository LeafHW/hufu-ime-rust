# 响应速度 / 资源占用 / 流畅度：重排关 vs 开（100 句实测）

- 语料：`docs/corpus/test_sentences_100.txt` 前 100 行（可录入 99 句，共 4256 个字母键 + 99 次空格上屏）
- 通道：**真实生产链路**（命名管道 `\\.\pipe\hufu-ime` → hufu-server → 引擎），非进程内压测
- 节奏：模拟真人 80ms/键、句间停 600ms（重排开的 B 相在停顿 350ms 防抖后触发后台打分）
- 两相先后同一 server 进程；测试后 server 已重启还原

## 逐键响应（字母键，n=4256）

| 指标 | A 重排关 | B 重排开 | 差 |
|---|---|---|---|
| 平均 | 16.70ms | 34.01ms | +103% |
| p50 | 7.37ms | 13.37ms | +81% |
| p95 | 59.14ms | 124.41ms | +110% |
| p99 | 75.63ms | 177.68ms | +135% |
| 最大 | 106ms | 241ms | +128% |
| >30ms 键数 | 985（23%） | 1561（37%） | +586 |
| >100ms 键数 | 2 | 413（9.7%） | +411 |

空格上屏：A 均 0.56ms；B 均 1.43ms（p95 5.8ms，含重排结果落盘路径）。

打分进行中连打（不等停顿，n=511）：均 42.96ms / p95 131.9ms / 最大 248ms —— **后台 Qwen 打分与前台解码争核，键延迟放大约 3 倍**。

## 资源占用

| 指标 | A 重排关 | B 重排开 |
|---|---|---|
| server 工作集 | ~306MB（稳） | 307→983MB（模型懒加载后） |
| 专用内存 | ~453MB | 1133MB |
| server CPU（打字期均摊） | ~2% 单核 | **5.4 核（34% 整机）/ 打分峰值 1s 窗口 7.5 核** |
| 关闭重排后内存 | — | **不回落**（988MB 保持，模型不卸载，需重启 server 回收 → 重启后 413MB） |

## 结论

1. **重排关（当前默认）**：p50 7.4ms、资源 306MB/2% —— 打字本体不受干扰；长句尾部的长尾（p95 59ms）来自 ngram 整句解码随 raw 增长，属解码器固有成本，可作后续优化方向（增量解码/限窗）。
2. **重排开**：每键延迟全面翻倍（打分抢核），>100ms 卡顿键从 2 个涨到 413 个；内存 +680MB；CPU 均值 1/3 整机。首句还有 ~8s 模型冷加载。
3. 建议：**默认关维持**；追求准确率的用户可开（设置页 `sentence.rerank.enabled`），代价如上。若后续要做「开也不卡」，方向是限核打分（专用小线程池）+ 打分让键（key 到达时暂停 gemm）+ 模型常驻改按需加载。

- 原始数据：`%TEMP%\latency-result.json`
