# 游戏输入兼容：从「逐游戏适配」转向「准入 + 兜底 + 自愈」

> 2026-11-01 方案稿。针对用户反馈：LOL 之外大量游戏键盘整体失效、切不走输入法、退出游戏也不恢复、必须重启。
> 现有实现见 `docs/game-host.md`（子类化流派定稿）与 `hufu-tsf/src/tsf.rs` 相关段落。

## 0. 结论先行

问题的本质不是「适配的游戏不够多」，而是三件事同时成立：

1. **判定点太早**：是否接管只在 `Activate` 一瞬间用「全屏形态 / 进程名白名单」判一次
   （`tsf.rs:883-909`）。游戏启动器、加载期、无边框全屏、`Activate` 时窗口还没建出来——
   任何一次漏判，就进入不可逆的失败路径。
2. **失败不可逆**：给文本无关窗口挂了 TSF 键 sink 之后，msctf/CUAS 的吞键管线一旦武装，
   `UnadviseKeyEventSink` 拆不掉（`game-host.md` 已实锤），于是「该进程整个键盘死 +
   切输入法也救不回」，只能杀进程。
3. **副作用外溢**：一旦用户把 `capslock` 映射成功能键，`caps` 的全局键盘钩子就会在**每个
   加载了本 DLL 的宿主进程各装一个、且装了不卸**（`tsf.rs:2642-2697`，安装点 `tsf.rs:3860`，
   条件 `caps_mapped`）。它把「一个进程的卡顿」放大成「全系统键路被牵连」，也正好是反作弊
   最敏感的行为之一。

所以正确方向不是继续加白名单，而是：

> **把「这是不是游戏」这个判断从架构里删掉，换成「这个进程配不配被接管」；
> 每次接管都必须可自动撤销；游戏内打字降级为可选的进程外输入。**

## 1. 三条失效链（症状 → 机理 → 证据 → 修法）

| # | 症状 | 机理 | 现场证据（trace 行） | 修法 |
|---|---|---|---|---|
| A | 游戏里键盘完全无反应，切别的输入法也没用，退出该应用才恢复 | 在**无 TSF 文档**的进程里挂了前景键 sink → CUAS 武装键盘接管管线，sink 零回调 | `activate: sink advised ok`（随后无任何键派发） | 准入制：没有真实 TSF 文档就不挂 |
| B | 键盘在整个系统都迟钝/失效，甚至退出游戏后仍坏，重启电脑才好 | 全局 `WH_KEYBOARD_LL`（`dwThreadId=0`）：**每个加载 DLL 的宿主各一条、全仓没有任何 `UnhookWindowsHookEx`**（`CAPS_LL_HOOK` 存了句柄却从不读）；回调里还做 `C:\ProgramData\HuFu\caps-no-hook` 的**文件系统 exists() 检查**（`tsf.rs:2538`）+ `GetForegroundWindow`。回调里做 I/O → 撞 `LowLevelHooksTimeout`；任一宿主线程饥饿/被反作弊挂起 → 全系统每键等超时；**杀游戏无效**（钩子同时长在别的常驻宿主里） | `capsll: LL 钩子就位（cap 映射在身）` | 钩子收口到单进程 + 回调零 I/O + 可卸载 |
| C | 某应用「从此打不了字」，重开该应用才好 | `GAME_HOST_MODE` / 子类化 / `ImmAssociateContextEx` 拆链 的残留（微信、explorer 已各中过一次）。拆链只记住**最后一个**焦点窗（`GAME_LAST_HWND` 单 cell），之前每个焦点窗永久断链 | `activate: 游戏宿主 → 子类化流派` 后该进程再也无键 | 状态机对偶 + 看门狗 + 自动黑名单 |
| D | 游戏里一按聊天键整个游戏像冻住/键盘失灵，几秒后缓过来 | 子类化 WndProc 里**同步**走管道 IPC（`ipc.rs:535`，2000ms/1000ms，最多两轮）——宿主 UI 线程被阻塞，按键排队，游戏消息泵停摆 | `E7: xxx consumed` 之后长时间没有下一条 | WndProc 内不许同步等待：先本地判定、异步回填 |

> 三条链的触发条件互不相同，所以「换一个游戏测」经常测不到同一个 bug；
> 反过来，只要把三条链各自堵死，就不需要认识任何一款游戏。

### 1.1 审计实锤与已排除项（2026-11-01 全仓扫描）

**实锤（按嫌疑度）**

1. `WH_KEYBOARD_LL` 全局钩子（`tsf.rs:2642-2697`，装在 `2663`，触发 `3860`，条件 `caps_mapped`）：
   每宿主一条、无卸载、**回调里做文件 exists() 检查**。这是全仓唯一真正坐在全系统键路上的东西。
2. 宿主进程内 `CreateProcessW` 拉起 `hufu-server.exe`（`ipc.rs:157-263`，`CREATE_NO_WINDOW`、无 Job 对象）：
   从**提权游戏**里拉起会继承高完整性级别，普通权限杀不掉；而它持有全局 Host 锁、全局热键和所有应用共享的会话态。
3. `ImmAssociateContextEx(hwnd,NULL,0)` 拆链不可逆，且只记最后一个窗口（`tsf.rs:9237-9289`）——
   代码注释自认「该应用从此打不了字，只有重装键盘/重启进程能救」。
4. 子类化 WndProc 内同步 IPC（`tsf.rs:9052 → 9117 → 9036`，`ipc.rs:535` 2s/1s）——游戏 UI 线程每键最多阻塞约 2-6 秒。
5. TSF sink cookie 存在**进程级** `Shared`（`tsf.rs:413-416`），多线程 Activate 会覆盖同一槽位 → 先前的 sink 永远摘不掉。

**已排除（不用再查）**：server 侧无任何 `SetWindowsHookEx` / `BlockInput` / `ClipCursor`；
DLL 无全局命名对象、无服务、无 HKLM 写、无 `ActivateProfile`/`SetDefaultProfile`；
`DllCanUnloadNow` 恒 `S_FALSE`（`lib.rs:79`）且钩子线程 `GetModuleHandleExW`（`2658`）钉住模块 →
不存在「钩子指向已卸载代码」的 UAF；管道 DACL 授 Everyone GA → 不存在「提权 server 锁死 ACL」。

## 2. 为什么「逐个游戏测」追不上

触发空间是笛卡尔积：图形 API（D3D/GL/Vulkan）× 输入栈（RawInput / DirectInput / IMM32 /
TSF / SendInput）× 反作弊 × 窗口形态（独占全屏 / 无边框 / 窗口化）× 启动阶段（启动器 /
加载 / 对局）× 权限（普通 / 提权）/ 多显示器 / DPI。

- 判定只错一次就失败，而测试要覆盖所有组合才敢说「兼容」。
- 每加一个名字，就多一个「名单没跟上」的失败点。现在 `shell_host_never_game`
  与 `comm_host_never_game`（`tsf.rs:9525-9566`）两个硬编码豁免名单，已经是这个模式的
  受害者：微信「偶发打不了字」、explorer 键盘全灭，都是名单/形态判定的补丁债。

## 3. 换判据：从「识别游戏」到「准入制」

### 3.1 三条正面证据（全部满足才允许接管）

- **P1 文本能力**：该进程出现过真实 TSF 文档焦点（可编辑文本服务 / 可编辑 ITfContext）。
  没有文档 = 这个进程不需要输入法 = 不挂 sink、不子类化、不拆链、不装钩子，**零副作用直通**。
  游戏、启动器、全屏视频、游戏内商店，天然落在这一档。
- **P2 管道健康**：与 `hufu-server` 的往返在阈值内、权限不越级（提权宿主连不上中等完整性
  管道）。不健康 = 只直通，不吞键。
- **P3 非高危画像**：具备以下任一特征 → 进「观察档」，不接管（或只接管、不回写系统状态）：
  - 加载了反作弊模块（ACE / TenProtect / EAC / BattlEye / Vanguard / XignCode …）；
  - 加载 D3D/Vulkan/DXGI 且**无**标准编辑控件；
  - 注册了 RawInput 且前台窗无 `WS_CAPTION`；
  - 是启动器/反作弊进程的子进程。

> 关键点：P1 让「游戏」这个类别自动消失——绝大多数游戏根本没有 TSF 文档，
> 不需要被名字、窗口形态、启动阶段识别。
>
> **可行性复核（2026-11-01，已核代码）**：只能做**进程级**——该进程从未出现过可编辑文档就
> **永不挂**；**「焦点一落到无文档窗口就 Unadvise」不可行**：① 已武装的 CUAS 摘不掉
> （`game-host.md` 实锤）；② 焦点抖动（WPS `GetFocus` 摇摆、Excel 4ms 重声明）会误摘，
> 而摘掉后没有重挂机制，比漏挂更糟；③ `pdimfocus.is_some()` **不能当证据**（dim 判据在
> 记分板/加载 overlay 上误判，代码注释已明确废弃）。
>
> 唯一可用的肯定证据是 edit session 内 `ITfContext::GetSelection` 成功（对应现有
> `caret_editable` 的 `selection_range` 路径，`tsf.rs:8775/8815`），但它现在是 **fail-open**
> （`None => true`），改准入制必须反过来 fail-closed。
>
> **落地前先上两行零风险探针**：`OnSetFocus` 加 `focdim: dim/top/act`、`Activate` 加
> `lazyprobe: top/sel`，在游戏 + 记事本 + VSCode + WPS 各跑一遍再定判据——因为现在游戏进程
> 从不挂 sink，`dispatch` 永不执行，这条判据在生产里**没有任何数据**。
> 另注意两个已知坑：`addword` 小窗线程自激活挂 sink（`addword.rs:700-724`，无焦点事件，必须显式豁免/补挂）；
> `UnadviseKeyEventSink` 用的是 `g.client_id`（首次激活 tid），多标签宿主会摘错线程。

### 3.2 同行对照：水杉输入法 2026-10 的同类修复（可直接抄作业）

水杉（Metasequoia IME，开源）在 2026-10 集中修了 CS2 / Dota 2 / 三角洲行动 / 英雄联盟
的一批游戏输入问题，结论与虎符现状对得上，可以直接对照核：

| 问题 | 水杉的结论 | 虎符现状（待核对） |
|---|---|---|
| 游戏里加载不了输入法 | CS2 的 Trusted Mode 只放行「系统目录 + 代码签名」的 in-proc DLL，装在 Program Files 会被直接拒绝加载；改成装到 `System32\IME\<厂商>\` | DLL 装在 `C:\Windows\SystemIME\HuFu\`（不在 `System32\IME` 下），且是 gnu 交叉构建、很可能**未签名**——起源 2 系游戏可能压根不加载 |
| 游戏自绘候选 | CS2/Dota2 在 `BeginUIElement` 回 `pbShow=FALSE`，但只替**内置白名单名字**（默认「拼音输入法」）画；解法=「游戏兼容（伪造名称）」把 IME 登记名改成白名单名，让游戏自己画 | 拿到 `pbShow=FALSE` 后**仍然弹自己的候选窗**（`candidate_ui.rs:381`，`tsf.rs:8844-8847` 明写"刻意双窗并存"）——自绘宿主上双候选/错位 |
| 独占全屏一打字就黑屏/掉独占 | 真凶是游戏不认 IME 时弹出的系统组合窗 `CiceroUIWndFrame`：它出现约 0.87s 后游戏退出独占模式；修法=前台是 D3D 独占全屏（`SHQueryUserNotificationState`）时不弹候选与提示 | grep 无 QUNS 相关判断——同样的黑屏风险存在 |
| 宿主卸载 DLL 后崩溃 | CS2 启动途中会加载又卸载 TSF DLL，线程池回调醒来跑进同地址映射的别的模块 → 崩溃；修法=`GetModuleHandleEx` 取模块引用 + `FreeLibraryWhenCallbackReturns` | 未见对应处理——"开着输入法启动游戏就崩"先排这里 |
| 翻页/选词与实际上屏不一致 | 引擎在按键回复之后才改候选页、从不通知 DLL，游戏画旧页而空格按新页上屏（LOL「选的和上屏的不一样」同族）；修法=UI-less 候选页推送 + 页码，DLL 只接受不旧于当前的页 | 虎符是 DLL 自绘/自拉取，需要单独核这条链路 |

> 这五条都是**确定性缺陷**，不依赖"猜游戏"，修一次覆盖一大片。
> 它们的共性是：问题不在"游戏太多"，而在"没按游戏/系统约定的协议办事"。

### 3.3 与现有子类化流派的关系

子类化（`game_subclass_proc`）不是废掉，而是**降级为「游戏内打字」的可选能力**：
默认关闭；用户显式打开「游戏输入」后，才在 P3 判定为游戏、且用户主动按热键开聊天时启用。
这样 99% 的用户在任何游戏里都只是「虎符没生效但键盘完好」，而不是「键盘死了」。

## 4. 三层防线

### 4.1 准入层（默认拒绝）

- `Activate` 不再做「游戏/非游戏」二分，只做「该进程有没有可编辑文档」的**一次**判定：
  这一判定在挂载前用探针拿到（见 §3.1），拿不到就**不挂**；挂上之后**不摘**（摘不掉，且抖动误摘）。
- 现有白名单/形态门**保留**，降级为「快速否决」——命中的直接不挂，省掉探测成本。
- 高危画像只影响「是否允许进入子类化/游戏输入」，不影响键盘直通。
- 任何接管都配 TTL 与自愈（见 §4.3），但自愈动作是**还原状态**，不是依赖 unadvise 去解除 CUAS。

### 4.2 兜底层（游戏里想打字时）

- **进程外输入条**：server 侧浮窗（复用候选窗的渲染/皮肤），热键或鼠标唤出，
  打字在浮窗里完成，提交时注入前台游戏（`WM_CHAR` / `SendInput` / 剪贴板三选一）。
- 完全不碰游戏的输入栈，因此对所有引擎与反作弊都安全；这是商业输入法通行做法。
- 独占全屏下浮层物理不可见（与现有候选窗同一限制），需游戏切无边框——文档里已写明。

### 4.3 自愈层（把「必须重启」变成「自恢复」）

- **DLL 看门狗线程**：任何接管都有 TTL；心跳断、宿主 N 秒不泵消息、连续 M 次引擎请求超时
  → 自动 `unadvise + restore + dissociate 还原`，并写自动黑名单。
- **server 监督**：前台进程切换 + `SendMessageTimeout(WM_NULL)` 探活；发现被我们接管过的进程
  无响应，主动下发撤销。
- **自动黑名单**：`%LOCALAPPDATA%\HuFu\game-hosts.auto.txt`（进程名 + 版本 + 时间），
  与人工 `C:\ProgramData\HuFu\game-hosts.txt` 分离，下次启动直接安全模式；设置页可一键清空。
- **一键急救**（键盘死了也能用鼠标点）：托盘菜单 / 桌面快捷方式 →
  结束 `hufu-server` → 需要时重启 `ctfmon` → 清残留状态 → 生成诊断包。
- 原则：**任何接管都要有 TTL 和外部撤销通道；不允许「装了就不卸」。**

## 5. 诊断层：让日志替你测游戏

现成通道已经够用（`tsf.rs:2858-2961`）：

- 开 trace：创建文件 `C:\ProgramData\HuFu\trace\trace-on`（热生效，无需重启），
  日志落 `C:\ProgramData\HuFu\trace\trace.log`（或 `%TEMP%\hufu-tsf-trace.log`）。
- 每行格式 `[epoch_ms] 进程名: 消息`，所以**一份日志就能看到这台机器上所有游戏的判定分支**：
  - `activate: sink advised ok` → A 链（危险）；
  - `activate: 游戏宿主 → 子类化流派（不挂 sink）` → 安全；
  - `E6 拆链` / `E7: 游戏窗子类化完成` / `capsll: LL 钩子就位` → 进入了哪些副作用。
- **加探针后**（§6 E4）还能直接回答「该进程有没有可编辑文档」：
  - `focdim: dim=true top=false` / `lazyprobe: sel=false` → 无文档（准入制该拒绝挂载）；
  - `esc caret probe: GetSelection ok=true` 且不出现 `gate: 非编辑焦点 → TestDown 不预吞` → 可编辑；
  - `sink advised ok` 之后该 exe **再无** `test vk=`/`key vk=` → A 链已武装。
- 做法：找 3-5 个反馈用户开 trace 复现一次，回传日志——
  **你不需要测游戏，日志会替你把每个用户机器上的游戏分类。**

配套两个小工具（P1）：

- **游戏体检探针**：对一个正在运行的游戏进程输出画像（模块、窗口样式、TSF 文档、
  RawInput、是否提权、管道 RTT），直接给 class 标签，用于把用户反馈映射到 A/B/C 链。
- **合成宿主回归**：6 个原型宿主（无文档普通窗、独占全屏 D3D11、提权进程、IMM32 应用、
  UWP/CoreWindow、被挂起线程的进程），自动化跑——测「输入栈类别」，不测「游戏标题」。

## 6. 立刻可做的四个验证（各 10 分钟）

- **E0 归因**：进游戏前先把输入法切成微软拼音（虎符不激活），再进同一款游戏。
  若键盘正常 → 问题在虎符（继续往下）；若键盘照样死 → 问题在游戏/反作弊层，
  虎符最多只能"不参与"，这条决定后面所有工作的方向。
- **E1 分类**：开 trace，进一款坏掉的游戏，看日志是 `sink advised ok` 还是 `子类化流派`。
  顺便看这份日志里**有没有该游戏 exe 的行**——没有行就说明 DLL 根本没被加载（落点/签名问题）。
  这一行决定后面走准入修法、加载修法还是子类化修法。
- **E2 钩子**：把 `capslock` 映射临时清空（或硬编码不装 LL 钩子）后重测同一款游戏。
  若恢复正常，B 链坐实——这就是「系统级死键 + 需要重启」的来源。
- **E3 救键**：键盘死时**先别重启**：任务管理器结束游戏残留进程 → 结束 `hufu-server`
  → 需要时重启 `ctfmon`，逐步记录哪一步恢复。
  顺便看 `hufu-server.exe` 的**完整性级别与父进程**——若它是被提权游戏拉起的，普通权限杀不掉，
  这就是「必须重启」的直接来源。
  这一步直接回答「重启到底救的是哪一层」，并给你一条「不重启」的急救流程。
- **E4 探针**（唯一的代码改动，零风险，只写日志）：`OnSetFocus` 加 `focdim: dim/top/act`、
  `Activate` 加 `lazyprobe: top/sel`，游戏 + 记事本 + VSCode + WPS 各跑一次。
  这一步决定准入制能不能做——判据不成立就退回「用能力强杀 + 自愈兜底」的保守路线。

## 7. 优先级

| 优先级 | 事项 | 目标 |
|---|---|---|
| P0 | **两行探针**（`focdim` / `lazyprobe`，只写日志零行为）+ E0 归因 | 用真实数据决定「准入制」能不能做，避免拍脑袋 |
| P0 | LL 钩子收口（单进程持有 + 回调零 I/O + 可卸载）+ 自动黑名单 + 看门狗 + 一键急救 | 消灭唯一能造成「全系统死键、杀游戏无效」的机制 |
| P0 | 协议合规清单（§3.2 五条：DLL 落点/签名、`pbShow`、QUNS 独占全屏门、DLL 卸载安全、候选页同步） | 一次性消掉「确定性游戏缺陷」，不依赖猜游戏 |
| P1 | 准入制（探针通过后：进程级「无可编辑文档永不挂、挂上不摘」）；进程外输入条；游戏体检探针；设置页「游戏输入」开关（默认关） | 游戏内可打字，且不影响安全默认值 |
| P2 | 合成宿主回归；反作弊画像库；trace 一键打包 | 新游戏/新反作弊上线时可快速定位 |
